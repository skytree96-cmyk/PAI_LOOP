# 메인페이지 UIUX 수정 제안

기준일: 2026-09-24 · 기준 코드: main `1ca6f53` · 검토 브랜치: `docs/mainpage-uiux-feedback-0924`

> 후속 결정: 사용자가 기존 톤 유지, 구현·배포, 우리 투찰률과 낙찰자 투찰률 모두 자동 계산을 승인했다. 아래는 최초 검토 시점의 제안이며, 실제 구현 범위와 검증은 [구현 기록](UIUX_MAINPAGE_IMPLEMENTATION_20260924.md)을 따른다.

## 제안의 핵심

전체 저장 규모와 현재 처리할 일을 분리하고, 공고 탐색에서 담당자 확인까지 같은 용어와 동선을 사용한다. 기존 파란색 상단 메뉴와 화면 구조를 유지하면서 문구, 숫자의 의미, 검색, 상세 이동을 먼저 개선한다.

이번 산출물은 수정 제안이다. 첨부 피드백을 검토 자료로 사용했으며, 문서 안의 삭제·변경 표현을 즉시 실행할 지시로 취급하지 않았다. 앱 코드, 데이터, 운영 배포는 변경하지 않았다. 원본 피드백 파일은 저장소에 복사하지 않았다.

## 작업 및 배포 기준

- 클로드의 기존 작업 디렉터리와 분리한 worktree를 사용한다. 원격 main을 새로 가져온 `FETCH_HEAD`에서 브랜치를 만들었다. 기존 체크아웃의 브랜치를 전환하거나 미커밋 파일을 복사하지 않았다.
- Google Cloud를 배포 기준으로 한다. 현재 Teams manifest와 워크플로 기본 주소는 Cloud Run을 가리킨다. Cloud SQL은 09/21 인계 기록에서 확인했다. 이번 검토에서 현재 운영 revision과 DB를 직접 조회하지 않았다.
- README와 AGENTS에 남은 Render 운영 설명은 과거 전제다. UI 변경 후 검증과 배포 계획에 Render 재배포나 Render DB를 넣지 않는다.
- 실제 구현 때는 당시 최신 main 및 클로드 변경과 다시 비교한 뒤 아래 묶음을 순서대로 적용한다. 현재 작업 중인 클로드의 미커밋 내용은 검토 범위에 포함하지 않았다.

## 1 오늘 할 일

상단 문구는 “지금 바로 확인하세요!”로 변경한다. 제목 아래에는 장황한 운영 설명 대신 현재 조회 범위와 갱신 상태를 한 줄로 표시한다.

현재 오른쪽의 큰 숫자 하나를 `저장된 전체 공고`와 `진행 중 공고`로 분리한다. 후자에는 `마감 전 · 종료·취소 제외`를 덧붙인다. 피드백의 `확인할 공고`는 실제로 확인이 필요한 업무 목록의 제목에 사용한다. 진행 중인 모든 공고가 담당자의 미처리 건이라는 인상을 주지 않는다.

본문은 네 가지 업무 카드를 같은 크기로 배치한다.

1. 판단이 필요한 공고
2. 검토 중인 공고
3. 마감 임박 공고
4. 결과 입력이 필요한 공고

카드는 현재 main에서 이미 도넛이 제거된 숫자 중심 구성을 유지하고, 각 카드의 집계 조건은 짧은 도움말로 옮긴다. 남아 있는 `활성 공고 대비` 설명은 재정리한다. 업무 카드가 서로 겹칠 수 있고, 개찰 후 결과 입력 대상은 진행 중 공고와 다른 범위여서 동일 분모의 비율이 오해를 만들 수 있기 때문이다. 비율을 추가한다면 카드별 모집단을 정의하고 표시해야 한다.

아래에는 부서별 공고 검토 현황을 둔다. 추천 기준 부서와 담당자의 실제 소속 부서를 구분한다. 선택한 부서의 추천·선택 수는 해당 조건의 목록으로 이어져야 한다. 집계 중은 `— / 현황을 불러오는 중`, 실패는 `현황을 불러오지 못했습니다 / 다시 시도`로 표시하고 0건으로 바꾸지 않는다.

## 2 공고 찾기

상단 메뉴는 `오늘 할 일 / 공고 찾기 / 입찰 검토 / 입찰 결과 / 회사 실적`으로 정리한다. 기존 경로와 공유 링크의 의미를 유지하고 표시 이름을 먼저 바꾼다.

검색 영역은 다음 순서로 구성한다.

1. 왼쪽 도움말 버튼과 `저장된 공고 / 나라장터에서 찾기 / 사전규격 찾기` 선택
2. 공고명·기관·공고번호 입력란과 눈에 보이는 `검색` 버튼
3. `진행 중 / 종료·취소 포함 전체` 조회 범위
4. 참가자격 확인 결과·AI 검토 의견·최종 판단 필터
5. 접어서 볼 수 있는 추천 기준 부서·우선 확인 키워드 설정

저장된 공고 아래의 긴 안내는 제거하고, 목록 위에 `저장된 공고 · 진행 중 · 검색 결과 N건`처럼 현재 상태만 남긴다. 도움말에는 저장소에 없는 공고를 나라장터에서 찾아 저장하는 방법을 설명한다. “부서에 매칭되지 않으면 제외됩니다”라는 문구는 현재 동작과 달라 사용하지 않는다.

검색창의 `/` 표시를 없앤다. 저장 공고에서도 검색 버튼이 보이게 하고, 버튼 클릭과 Enter가 같은 검색 경로를 실행하도록 맞춘다. 새 검색·조건 변경 시 페이지를 1로 되돌리고 연속 요청의 이전 응답이 최신 검색을 덮지 않게 한다. 실제로 키보드 단축키를 유지할지 여부는 별도 구현 선택이며, 표시 제거 때문에 다른 입력 동작을 바꾸지 않는다.

`선택한 조건 초기화`는 초기화되는 범위를 명시한다. 공고 찾기의 기본값은 진행 중으로 유지하되 전체 저장 숫자를 눌러 진입한 경우에는 종료·취소 포함 전체를 명시적으로 적용한다. 기간·자격·담당자 판단 필터가 남아 전체 건수가 줄어드는 상황을 막는다. 현재는 검색어 입력 시 전체 상태로 범위가 넓어진다. 이 동작을 유지할 때도 `전체 저장에서 검색 중`이 보이게 하고, 사용자가 진행 중을 명시적으로 선택한 경우에는 그 범위를 존중하도록 정리한다.

## 3 공고 상세

### 요약과 주요 확인 사항

요약에는 핵심 결론, 참가자격 확인 결과, 지금 확인할 사항만 남긴다. `회사 기준과 비교`는 요약에서 제거하고 `주요 확인 사항` 안에서 관련 근거와 함께 제공한다. 기존 공개·권한 계약을 유지하고 비공개 자료만 기존 권한으로 제한한다. 공개 프로필 비교에 새로운 로그인 장벽을 만들거나 해당 비교 API·사실 검증 자체를 삭제하지 않는다.

`담당자 검토` 카드와 `근거` 탭을 `주요 확인 사항`으로 통합한다. 항목마다 `확인할 내용 → 확인이 필요한 이유 → 원문 위치 → 연결 자료` 순으로 보여준다. 제출 확인과 참가자격 판단은 의미가 달라서 통합 탭 안에서도 구분한다. 모든 확인 사항에 원문 근거가 존재한다고 가정하지 않는다.

피드백의 토글은 사용자가 PASS·REVIEW·FAIL을 직접 바꾸는 스위치가 아니라 **조건별 설명을 펼치는 아코디언**으로 해석한다. `충족`은 초록, `확인 필요`는 노랑, `미충족`은 빨강으로 표시하고 문구와 아이콘을 함께 쓴다. 확인 필요·미충족 항목은 먼저 보여주고 기본으로 펼친다. 조건부 충족은 조건을 함께 표시하며 무조건 충족으로 합치지 않는다.

`R07` 같은 내부 코드는 기본 문장에서 숨긴다. 사용자에게는 실제 미확인 조건과 다음 확인 행동을 풀어 쓴다. 내부 판정 코드·저장 기록·감사 근거는 유지한다. 현재 근거가 없으면 그 사실을 말하고 임의의 사유를 만들지 않는다.

계약방식은 먼저 `pps_enrichment.py`의 수집 매핑과 `schemas.py`·`api.py` 응답을 연결한다. 원본 payload 전체를 공개하지 않고 최신 유효 자료에서 허용한 계약방식 값과 확인 상태만 전달한다. 값이 누락된 경우 `계약방식 미확인`, 자료가 서로 다른 경우 `계약방식 확인 필요 · 자료 간 표시가 다릅니다`처럼 나눈다. 확인된 값에는 확보된 원문 위치를 연결한다. 미수집·원문 미기재·자료 충돌은 실제 상태를 입증할 수 있을 때만 구분하며 추측하지 않는다.

### 탭과 근거 이동

탭 이름은 `요약 / 주요 확인 사항 / 정량 점수·주의사항 / 최근 3년 낙찰 이력 / Teams 알림 미리보기`로 정리한다. 예상·확정·부분 소계가 모두 존재하므로 탭 전체를 예상 점수로 단정하지 않는다. 개별 점수의 확정·잠정·계산 보류 표시는 유지한다.

- 일반 탭 클릭은 해당 패널의 첫 내용이 고정 탭 바로 아래에 오도록 상세 스크롤 컨테이너만 이동한다.
- `근거 보기`는 연결된 근거 항목으로 이동하고 짧게 강조한다. 근거 ID가 없으면 주요 확인 사항 첫머리에서 연결 자료가 없음을 알려준다.
- 근거 이동과 일반 탭 이동을 하나의 처리로 뭉치지 않는다. 예를 들어 `selectTab(tab, { targetEvidenceId, resetScroll })`처럼 의도를 구분한다.
- 바깥 목록의 스크롤은 유지한다. 고정 헤더 높이와 모바일 탭 줄바꿈을 고려한다. 키보드 포커스는 이동한 탭 또는 목표 항목으로 이어지게 한다.

### 모서리와 간격

현재도 8/14/22px 반경 토큰과 둥근 카드가 적용되어 있으므로 일괄 재디자인이 필요한 상태는 아니다. 추천 정리값은 입력·버튼 8px, 카드 14px, 상세 패널 18px다. 기존 CSS 토큰을 정리해서 적용하며, 중복 스타일에서 제각각 덮어쓰는 값을 줄인다. 작은 설명 글자의 권장 최소 크기는 13px로 통일한다. 현재 일부 11~12px 예외가 있어 함께 점검한다. 360px 화면에서는 카드와 긴 탭을 줄바꿈하여 화면 밖으로 밀리지 않게 한다.

## 4 입찰 결과

설명 제목은 `자동 반영된 결과도 담당자가 최종 확인합니다`로 바꾼다. 본문은 자동 반영·수정·출처 확인의 순서로 설명한다. 자동 동기화가 현재 확인되지 않았다면 완료된 것처럼 표현하지 않고 상태를 구분한다.

결과 화면은 `나라장터에서 반영된 결과`와 `담당자 확인 기록`을 구분해 출처·수집 시각·확인 상태를 보여준다. 자동 수집 원본은 유지하고 담당자 수정은 별도 검토본에 저장하는 기존 계약을 따른다. 값이 다른 경우에는 어느 필드가 다른지 표시하고, 출처와 필수값이 있어야 `확인 완료`로 저장되게 한다. `VALIDATED` 등 서버 상태 값은 표시 문구 변경으로 바꾸지 않는다.

금액은 원 단위를 유지하면서 `12,345,000`처럼 세 자리마다 쉼표를 표시한다. 숫자 입력의 표시값과 저장값을 분리하고 기존 소수 허용 정책을 임의로 바꾸지 않는다. 붙여넣기·중간 자리 수정·빈 값·소수 입력·잘못된 문자를 검증한다. API에는 쉼표 없는 숫자를 전송한다.

우리 투찰률은 이미 있는 자동 계산 모드를 활용한다. 유효한 기준가격과 출처가 있으면 자동 계산을 기본으로 제시한다. 없으면 `기준가격을 확인하면 자동 계산됩니다`를 표시하고 수기 입력을 선택할 수 있게 한다. 기준 종류, 금액, 출처를 함께 보여주며 서버 재계산을 유지한다. 추정가격이나 예산을 확인 없이 기준가격으로 대체하지 않는다.

피드백의 “낙찰률”이 낙찰자 투찰률을 뜻한다면 별도 필드 개선이 필요하다. 우리 투찰률만 자동화하고 요청이 모두 해결됐다고 보고하지 않는다. 낙찰금액과 동일한 기준가격이 확인될 때만 계산할 수 있게 하고, 값이 부족하면 `계산 불가 · 기준가격 확인 필요`로 남긴다.

## 구현 후 검수 기준

- 합성 데이터에서 전체 저장 1,200건과 진행 중 480건을 별도로 표시하고 클릭한 목록이 각 조건을 따른다. 이 숫자는 검수 예시이며 운영 값이 아니다.
- 1,001건 이상에서 마지막 페이지까지 누락·중복 없이 조회한다. 부서 추천 순서 변경 전후에 결과 집합과 건수는 같다. 같은 공고의 재분석 기록이 여러 개여도 공고 수는 한 건이다.
- AI 검토 완료 지표를 도입한다면 최신 원문·마감·현재 첨부 전체의 유효성 검사를 통과한 공고만 센다. 부서의 키워드 추천 수를 AI 분석 완료 후속 단계인 것처럼 표시하지 않는다.
- 저장된 종료·취소 공고, 미분류 공고, 다른 부서 관련 공고를 전체 범위 검색에서 찾을 수 있다. 부서 추천 변경만으로 공고가 사라지지 않는다.
- 검색 조건 공유 링크와 뒤로 가기에서 필터·페이지·목록 위치가 복구된다. 빈 검색과 초기화도 정의된 범위를 따른다.
- 집계·근거 조회의 미완료, 실패, 권한 제한을 0건이나 완료 상태로 표시하지 않는다.
- 충족·조건부 충족·확인 필요·미충족이 색 없이도 구별되고, 아코디언은 키보드로 열 수 있다. 자격 결과와 AI 의견·담당자 최종 판단은 독립적으로 남는다.
- 상세의 각 탭을 길게 스크롤한 후 전환해도 첫 내용이 보이고, 근거 보기 버튼은 해당 항목에 도착한다. 360px·768px·1440px에서 확인한다.
- 0원·빈 금액·소수·쉼표 붙여넣기·기준가격 없음·0인 기준가격·출처 없음·수기 전환·저장 후 재열기를 검수한다. 자동 반영 원본과 담당자 검토본의 관계를 보존한다.
- 관련 기존 검증: test_frontend_public_contract.py, test_top_navigation_frontend.py, test_dashboard_work_queues.py, test_dashboard_loading_frontend.py, test_dashboard_department_coverage.py, test_notice_filter_links_frontend.py, test_result_entry_frontend.py, test_result_learning_bid_rate.py, test_outcomes_api.py. 실제 변경에 맞는 테스트부터 실행하고 저장소의 필수 CI를 따른다.

이번 제안에서는 소스 대조와 문서 일관성 검토를 수행했다. 앱 행동을 변경하지 않았으므로 앱 테스트나 운영 배포를 실행하지 않았다.
