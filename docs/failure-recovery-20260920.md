# 실패 로그 확인과 복구 경계 — 2026-09-20

운영 Cloud SQL은 읽기 전용 트랜잭션으로 확인했다. 분석 실행, 운영 데이터 수정,
유료 모델 호출, 배포는 이 점검에 포함하지 않았다. 아래 수치는 점검 당시의 관찰값이다.

## 확인한 실패

- 최근 7일 추출 기록에 20,000 출력 토큰 상한 실패 51회, 입력 거절 36회,
  모델 실행 실패 53회가 있었다. 동일 공고의 재시도가 포함된 횟수다.
- 입력 거절과 모델 실행 실패는 세부 원인이 저장되지 않아 과거 기록만으로
  입력 크기, 스키마, 시간 초과 등을 확정할 수 없었다.
- 최근 추출을 시도한 유효 OPEN 공고 25개 표본 중 하나는 첨부가 11개였다.
  공통 manifest 상한은 12개지만 진단 응답 상한이 10개여서 `UNAVAILABLE`로 떨어졌다.
  이 표본은 전체 공고의 무작위 표본이 아니다.

## 수정한 동작

1. 진단 응답이 공통 `MAX_MANIFEST_ATTACHMENTS` 상한을 사용한다. 11·12개 슬롯을
   모두 반환하고, 상한을 넘는 manifest는 기존 invalid-slot 경고와 미완료 상태를 유지한다.
   실제 문제 공고를 수정한 로컬 코드와 운영 DB 읽기 전용 연결로 확인한 결과,
   `UNAVAILABLE`에서 `OK`로 바뀌고 첨부 11개가 모두 반환됐다.
2. 일반 분석은 문서를 다시 다운로드·파싱한 후에만 이전의 엄격히 확인된 20k 상한
   실패를 재사용한다. 현재 계약·모델·manifest·문서 및 source/input 지문이 일치해야
   하며, 같은 실패 행을 추가하거나 모델을 다시 호출하지 않는다. 원문이나 계약이
   바뀌면 기존 처리로 진행한다. 명시적인 `LONG_OUTPUT_ONCE` 경로는 별도로 유지한다.
3. 게이트웨이 입력 거절과 모델 실패에 단계별 고정 `detail_code`를 추가한다.
   원시 예외 문장, 요청 본문, 공급자 응답은 저장하지 않는다. 확인할 수 없는 오류는
   고정 unknown 코드로 남긴다. 기존 세부 코드 없는 오류 형식도 계속 수용한다.

## 적용과 다음 확인

API와 W13 workflow 변경이 모두 적용되어야 새 세부 실패 코드가 서버 진단까지
전달된다. 새 workflow를 먼저 적용하면 구버전 API가 새 detail을 거절할 수 있으므로
기존 오류도 수용하는 API를 먼저 적용한 뒤 W13을 적용한다. 저장된 과거 실패에
새 원인을 소급해서 붙이지 않는다. credential과 publication allowlist는 바꾸지 않는다.

이번 수정은 정량점수 산출 성공을 의미하지 않는다. 실제 문제 공고도 첨부 진단은
복구됐지만 정량 상태는 `INCOMPLETE`였다. 점수표·인용·회사 사실의 검증을 통과하지
못한 결과를 확정 점수로 승격하지 않는다. 토큰 상한, 모델, 자동 재시도 예산도
늘리지 않는다.

후속 운영 검증은 새 진단으로 실패 유형을 구분한 뒤 정확한 공고·첨부와 실행 예산을
정해 수행한다. 32k 단건 실행은 [기존 정책](long-output-once.md)의 명시적 경로를 따른다.
