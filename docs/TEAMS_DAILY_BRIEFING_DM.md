# 개인 Teams 데일리 브리핑

매일 아침 공고 브리핑을 팀 채널이 아니라 **본인의 Teams 개인 채팅**으로 보냅니다.
봇을 연결한 사람이 받으며, 연결이 곧 구독입니다. 별도 동의 절차는 없습니다.

## 채널과 무엇이 다른가

채널 브리핑은 모두에게 같은 목록을 보냈습니다. 개인 대화는 받는 사람이 누구인지
알 수 있으므로, **그 사람의 부서 기준으로 우선순위를 다시 계산해** 보냅니다.
부서가 없는 계정(`ADMIN`)은 기존과 같은 전체 기준 브리핑을 받습니다.

우선순위 계산식 자체는 바뀌지 않았습니다. 기존에는 그 공고에 가장 잘 맞는 부서의
적합도를 쓰던 자리에, 받는 사람 부서의 적합도를 넣습니다. 부서별 점수는 이미
저장·계산되던 값이며 새로운 채점 로직을 추가하지 않았습니다.

## 두 가지 발송

| 종류 | 시점 | 근거 게이트 | 카드 제목 |
| --- | --- | --- | --- |
| `DAILY` | 한국시간 08:30 | 그날 수집·분석 완료 확인 | 오늘의 공고 브리핑 |
| `SUBSCRIBED` | 연결 직후 | 없음 | 지금 기준 공고 브리핑 |

`DAILY`는 그날의 정리된 결과를 대표하므로, 수집·분석이 끝나지 않았으면 보내지
않습니다. 08:30부터 6시간 안에 조건이 갖춰지지 않으면 그날은 건너뛰고 다음 날
브리핑이 다음 발송입니다. 지난 아침을 저녁에 소급 발송하지 않습니다.

`SUBSCRIBED`는 그날의 요약이 아니라 연결 시점의 스냅샷이므로 같은 게이트를 걸지
않습니다. 대신 카드가 스스로 "연결 시점 기준"임을 밝힙니다. 이 메시지가 연결이
성립했다는 확인 역할도 합니다. 봇은 연결 명령에 답장하지 않기 때문입니다.

## 중복 방지와 장애

예약은 `teams_briefing_deliveries`에 저장되며 `(수신자, 한국시간 날짜, 종류)`가
유일합니다. 서버 재시작, 워커 다중 실행, 같은 날 재연결 어느 경우에도 같은 사람에게
같은 브리핑이 두 번 가지 않습니다.

상태는 관심 공고 알림과 같은 경계를 씁니다. `SENT`는 Connector가 수락한 상태이며
읽었다는 뜻이 아닙니다. `RETRY`는 명시적 재시도 가능 오류로 최대 5회입니다.
**`UNKNOWN`은 전송 후 결과가 불명확한 경우이며 자동 재전송하지 않습니다.** 실제
도달 여부는 Teams 대화에서 확인합니다. 수신자가 비활성이면 `CANCELLED`,
발송 창이 닫힌 뒤 처리되면 `SKIPPED`로 남습니다.

## 설정

```
PAI_TEAMS_BRIEFING_ENABLED=true     # 기본값 false. 이 값이 없으면 워커가 뜨지 않습니다
PAI_TEAMS_BRIEFING_HOUR=8           # 선택, 기본 8
PAI_TEAMS_BRIEFING_MINUTE=30        # 선택, 기본 30
```

개인 봇 설정(`PAI_TEAMS_BOT_APP_ID` 외 3개)이 유효하지 않은 상태에서 이 값을 켜면
애플리케이션이 시작하지 않습니다. 추가 테이블은 앱 시작 시 생성되며 기존 데이터를
보존합니다. 상시 실행 환경이 아니면 08:30 발송을 보장할 수 없습니다.

## 검증

```bash
python -m pytest tests/test_briefing_delivery.py tests/test_teams_sidebar_runtime.py
node --check src/pai_loop/static/app.js
```

합성 수신자·계정·공고와 격리된 테스트 DB를 사용하며 실제 Teams로 보내지 않습니다.
발송 창 경계, 준비되지 않은 날의 발송 금지, 같은 날 재연결, 비활성 수신자,
불명확한 결과의 재전송 금지, 모르는 부서 ID의 안전한 대체를 확인합니다.
