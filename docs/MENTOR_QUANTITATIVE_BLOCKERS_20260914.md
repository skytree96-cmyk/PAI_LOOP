# PAI_LOOP 정량점수 — 멘토 검토용 오류·미해결 과제
작성: 2026-09-14 / 코드 기준: `f6b51ba1d8615d83bccfa133f6cf28bb5fb4b808`
브랜치: `feat/quantitative-newpc-resume-0914`

## 멘토에게 드리는 핵심 질문

정량점수의 산술 엔진은 작동하지만 실제 공고 총점은 아직 확보하지 못했습니다. 우리는 “원문 평가규칙 + 검증된 회사 사실 → 항목별 점수”를 제공하려고 합니다. 지금까지 첨부 선택·원문 해석·검증기 보강을 많이 했지만, 이 작업이 실제 계산 제공을 얼마나 앞당기는지 다시 판단하고 싶습니다.

**전면적인 추출 자동화보다 먼저, 제한된 사업군에서 사람이 확인한 규칙과 원본 회사 증빙을 연결하여 항목별 계산을 제공하는 것이 맞을까요? 그렇다면 어디까지 기계 검증하고 어디부터 사람의 명시적 승인을 받아야 할까요?**

이 문서는 원문·회사 값·실제 공고 ID·비밀정보를 제외한 검토 자료입니다. 과거 장애의 원시 로그를 모두 확보한 것은 아닙니다. 아래에서 문서에 남은 역사적 기록, 현재 코드/SYN 재현, 로컬 저장 입력 재생을 구분합니다. 운영 DB·서비스를 다시 조회한 결과는 아닙니다.

## 1. 확인된 현재 상태

처리 흐름: 공고/첨부 → 구조화된 원문 규칙 → 원문·표·조건 검증 → 회사 증빙 연결 → 결정적 점수 계산.

| 검증 범위 | 확인한 결과 | 해석 |
|---|---|---|
| 동일 저장 입력 49공고(19+30, 중복 0) | 49/49 기존 점수 결과 동일. 1공고에서 잠정 항목 점수 2개, 수치 총점 0공고 | 신규 총점 복구 0. 항목 점수도 이번에 새로 복구된 것은 아님 |
| 첫 차단 계층, 분모 49 | 첨부/기록 커버리지 44, 기타 규칙 검증 4, 규칙 통과 후 회사 입력 미산정 1 | 공고별 첫 계층을 하나만 배정한 수치 |
| 30공고 중 native/raw 대조 가능한 18공고 | 1개 로컬 활성, 17개 검토. 점수·범위·활성 상태 18/18 기존 경로와 동일 | 18건은 위 49건의 부분집합. 추가 총점 복구 0 |
| 18공고의 첨부 검사 101개 | native/raw 대조 74, ZIP 내부 페이지 미증명 4, 입력 누락 19, parser 불완전 4 | 74는 규칙 AVAILABLE/점수 성공 건수가 아님 |
| 나머지 12/30공고 | native digest 미확정 9, 현행 metadata schema 미확인 3 | ID·해시·manifest를 만들어서 실행하지 않음 |
| 별도 3사례의 사람이 구성한 규칙 + 실제 회사 부분 스냅샷 | 8행 중 재무 2행만 잠정 수치, 신용 3행 미산정, 나머지 3행 검토 | 전체 첨부 승인 규칙이 아니므로 운영 복구 수에 합산하지 않음 |

최근 구현:
- 자동 경로와 로컬 검증이 같은 회사자료 resolver를 사용하도록 연결했습니다.
- generator 입력이 첫 조회에서 소진되어 후속 재무·인력 조회가 비던 오류를 수정했습니다.
- native 바이트·raw·전체 manifest를 확인한 뒤 기존 compiler/회사 resolver/점수 엔진으로 이어지는 로컬 CLI를 추가했습니다.
- 결과는 LOCAL_REVIEWED_QUANTITATIVE_PREVIEW이며 운영·저장·전체 원문 승인 권한은 없습니다.
- main 병합·배포·유료 호출·운영 접근은 하지 않았습니다.

### 측정·설명의 오류

- 과거 “필요 첨부에 도달하지 못함”을 프롬프트가 표를 잃는 회귀로 오인했습니다. 당시 `ATTACHMENT_CONTINUATION_REQUIRED`가 남아 있었습니다.
- 9/11에는 다른 종류의 레코드를 첨부 읽기 실패로 포함해 152건으로 부풀렸고, 실제 읽기 실패는 약 4건으로 정정했습니다.
- 검증기 확장 효과도 비교값·항목 총점을 실제 배점 근거로 잘못 세어 170개로 예상했다가 6개로 정정했습니다.
- 제안요청서와 과업지시서를 한 집단으로 묶어 첨부 선택 효과를 오해했습니다. 과거 표 포함률·비용 수치는 당시 표본의 결과이며 현재 운영 수치가 아닙니다.
- “재검증은 반드시 새 유료 추출”이라는 설명은 틀립니다. 저장 raw/원본 bytes가 보존된 범위는 무료 검증이 가능합니다. 단, 무료 재검증 성공 자체가 전체 첨부 승인이나 점수 복구를 뜻하지 않습니다.
- 이전 3사례의 7행 조건부 일치는 가정 회사 입력으로 계산한 결과였습니다. 실제 회사자료 검증으로 해석하면 안 됩니다. 최신 실제 입력 대조에서는 별도 재무 2행만 수치가 나왔습니다.
- REVIEW를 모두 원문 결함으로 세면 안 됩니다. 회사 binding 불일치와 미증명 실적 조건도 REVIEW가 됩니다.
- 현재 코드에는 HWP reader가 있으므로 과거 “모든 HWP 미지원” 설명을 반복하지 않습니다. 실제 파싱 결과를 확인합니다.

## 3. 남아 있는 차단 코드와 의미

다음은 예외 로그와 구분해야 하는 정상 보호 판정도 포함합니다. 이를 단순히 없애는 것은 해결이 아닙니다.

| 코드/상태 | 의미 | 필요한 해결 |
|---|---|---|
| VALIDATED_RECORD_MISSING / ATTACHMENT_INCOMPLETE | 현행 전체 첨부에 필요한 검증 기록/입력이 없음 | 누락된 실제 원본·기록 확보와 올바른 연결 |
| EXTRACTION_CONTRACT_PROOF_INVALID / DOCUMENT_BINDING_MISMATCH / MANIFEST_BINDING_MISMATCH | 계약·문서·현행 첨부 식별 관계가 맞지 않음 | 기록의 원래 의미와 버전을 보존한 재검증 경로. 최신 계약을 덧씌우지 않음 |
| TABLE_TOTAL_MISMATCH / *_LITERAL_MISMATCH / CASE_* / REQUIRED_EVIDENCE_INCOMPLETE | 소계·인용·배점·필수 근거가 원문 또는 규칙 모델과 불일치 | 정량/정성/가격 소속과 표·행 소유관계까지 검증 |
| FACT_DIMENSIONS_UNMODELED / MANUAL_CONDITIONS_REMAIN | 인정범위 해석 실패 또는 자동 증명할 수 없는 추가조건 | 실적별 증빙과 원문 조건을 대조하거나 명시적 사람 확인 절차 |
| 회사 binding/payload 불일치 | 값만 있어도 해당 항목의 검증 증빙으로 사용할 수 없음 | 원래 ID·값·단위·유효기간·원본 위치·payload를 보존한 입력 |
| UNPROVEN / ATTESTED_ONLY | EOF·임의 줄 상한은 표 종료 증명이 아님. literal 파싱만으로 원문 승인을 할 수 없음 | 종료/소속/참조 범위 증명과 승인 모델 |
| PDF_PAGE_TEXT_UNVERIFIED / NATIVE_MEMBER_TEXT_COVERAGE_UNVERIFIED | 새 로컬 preview의 페이지·archive 확인 부족 | 페이지/member 단위 감사. 임의 누락 허용 금지 |
| GOLDEN_NOTICE_NOT_IN_SNAPSHOT | 합성 조건부 golden과 실제 공고의 identity가 다름 | 실제 사례의 독립 기대값 작성. ID를 바꿔 통과시키지 않음 |

회사 부분 스냅샷의 사실 3개 모두 원래 identity/link가 빠져 있습니다. 저장 의미 payload digest가 있는 2개도 부분 입력 재구성과 0/2 일치합니다. ID뿐 아니라 `value_label` 등 원래 필드가 없으므로, ID를 만들거나 hash를 다시 계산해 “검증됨”으로 바꿀 수 없습니다. 이것은 로컬 export의 한계이며 운영 회사 증빙 자체가 없다는 결론은 아닙니다.

대표 실적 조건은 계약별 연간 금액, 참가자 수, 고정 인정기간, VAT, 공동계약 지분, 발급·승인 근거입니다. 사용자에게 “확인 어려운 실적만큼 감점” 의도는 있지만, 데이터 없음과 원문상 0점/미제출은 다릅니다. 검증된 실적만 집계한 보수적 추정과 최종 확정을 어떻게 구분할지 정책 결정이 필요합니다.

## 5. 멘토에게 결정받고 싶은 5가지

1. **최소 제품 범위:** 교육·연수·컨설팅의 검증 가능한 10~20공고에서 “확인된 항목 소계 + 잠정 범위 + 미확정 배점”을 먼저 제공할까요? 전체 총점까지 기다릴까요? 사용자에게 실제로 유용한 최소 출력과 금지해야 할 표현을 정하고 싶습니다.
2. **개발 순서:** 원문 참조·표 종료·소속 자동 증명을 먼저 끝낼지, 사람이 확인한 규칙의 승인/개정/철회 기능을 먼저 만들지 판단을 부탁드립니다. 두 방식 모두 전체 추출을 다시 만드는 대신 기존 계산 엔진을 재사용합니다.
3. **회사 증빙 모델:** 재사용 가능한 신용·재무 “원본 사실”과 공고별 조건 적용 증명을 분리할까요? 원본 사실의 수명/해시와 criterion binding을 어떻게 설계해야 재추출 때 불필요한 재등록을 줄이면서 오래된 조건 적용을 막을 수 있을까요?
4. **보수적 실적 계산 정책:** 추가조건 미확인 실적을 제외한 잠정 계산을 허용한다면, 검증된 0건·미제출·증빙 부족을 어떻게 구분하고 하한/상한을 표시해야 할까요? 확인되지 않은 값을 0으로 만들어 원문 최저점이나 만점을 내는 것은 금지하려 합니다.
5. **다음 실행의 합격 기준:** 같은 실제 입력에서 신규 계산 공고/항목, 과대계산, 미확정 배점, 사람 검토시간, 유료 비용을 어떤 우선순위로 평가할까요? 독립적인 항목별 golden을 먼저 확정한 뒤 작은 유료 표본을 승인하는 순서가 적절할까요?

권장 다음 단계는 원본 회사 증빙 export의 누락 필드를 확보하고, 선정한 소수 공고의 항목별 기대값(만점·회사 값·예상 점수·확정/추정)을 독립적으로 작성해 무료 replay로 대조하는 것입니다. 운영 재추출을 먼저 늘릴 근거는 아직 확보하지 못했습니다.
