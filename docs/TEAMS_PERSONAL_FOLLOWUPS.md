# Teams 개인 관심 공고 알림

공고 목록·상세 화면의 **관심 등록**을 누르면 해당 공고를 본인의 관심 목록에
저장합니다. **관심 공고 · Teams 개인 알림**에서 연결 상태, 전체 관심 공고,
예약·발송 결과를 확인하고 등록을 해제할 수 있습니다.

## 수신자와 알림 내용

부서 로그인 계정을 개인 수신자로 간주하지 않습니다. 현재 로그인 세션에서
발급한 일회용 연결 명령을 본인의 PAI 봇 개인 대화에 보내야 연결됩니다.
같은 부서 계정을 사용하는 두 사람도 관심 공고와 알림 대상을 각각 관리합니다.
재로그인하면 본인 Teams에 다시 연결하여 기존 관심 공고를 불러옵니다.
로그아웃은 이미 등록한 알림을 취소하지 않습니다. 관심 해제나 Teams 연결 해제,
봇 제거, 등록 당시 부서 계정의 비활성화는 후속 발송을 막습니다.

카드는 발송 시점에 저장된 최신 공고와 검증된 분석으로 생성됩니다.

- 공고명·발주기관·사업금액·마감 시각
- 참가자격 판정과 원문에 연결된 검증된 자격조건 요약
- 정량 총점·항목별 배점과 점수, 확정·추정·산정 불가 구분
- 자격·준비 리스크와 3년 유사공고 기반 경쟁·집중 리스크
- 분석·첨부 검증 상태, 시스템 검토 의견과 확인 조건
- 공고 상세의 전체 분석·원문 근거로 이동하는 버튼

카드에 들어가는 조건·점수 항목은 길이를 제한하여 요약하고 나머지는 상세
화면에서 확인합니다. 점수가 없다고 0점을 넣거나 리스크로 자격 판정을 바꾸지
않습니다. 카드 생성은 저장 데이터를 읽으며 모델 호출이나 재분석을 하지 않습니다.
원본 파일, 내부 증빙 값, 제공자 응답·비밀값은 메시지에 복사하지 않습니다.

## 예약 정책

| 시점 | 예약 시간 | 동작 |
| --- | --- | --- |
| 관심 등록 | 등록 직후 | DB 큐 저장 후 다음 발송 주기, 기본 30초 내 시도 |
| 마감 5일 전 | 한국시간 오전 9시 | 해당 날짜 안에서만 재시도 |
| 마감일 | 한국시간 오전 9시 | 공고 마감 전까지만 재시도 |

마감이 오전 9시 이전이면 당일 알림은 마감 30분 전으로 앞당깁니다.
자정을 넘지 않도록 조정하며, 정확히 자정 마감은 전날 23:30에 예약합니다.
등록 시 이미 지난 단계는 생략하며, 당시 등록 알림에 최신 내용을 담습니다.
공고 마감이 바뀌면 아직 보내지 않은 단계를 새 마감으로 다시 예약합니다.
이미 발송하거나 결과가 불명확한 단계는 같은 등록에서 반복하지 않습니다.
마감·취소·대체 공고에는 신규 등록을 허용하지 않으며, 기존 예약도 발송 전
현재 상태와 최신 PPS 기준을 확인합니다. 관심 해제 후 재등록은 별도 회차입니다.

## 발송 상태와 장애 복구

예약과 발송 이력은 PostgreSQL/SQLite의 별도 테이블에 저장됩니다. 서버 재시작이나
중복 클릭에 의존하지 않으며, 워커는 원자적인 선점과 발송 전 상태 재검사를 합니다.

- `PENDING`, `CLAIMED`, `SENDING`: 예약·선점·발송 처리 중
- `SENT`: Connector가 메시지 ID로 수락한 상태. 사용자가 읽었다는 의미는 아님
- `RETRY`: 명시적 재시도 가능 오류. 최대 5회, 지수 지연과 Retry-After 적용
- `UNKNOWN`: 전송 후 연결 단절·응답 불명·발송 중 프로세스 종료. 자동 재전송하지 않음
- `FAILED`: 영구 거절 또는 재시도 소진
- `SKIPPED`, `CANCELLED`: 지난 단계 생략 또는 관심 해제·공고 상태 변경

`UNKNOWN`은 Teams 대화에서 실제 수신 여부를 확인합니다. 발송 중 이미 외부에
전달된 요청은 관심 해제로 회수할 수 없습니다. 동일 회차의 실패 이력은 지우지
않습니다. 원인을 해결한 뒤 사용자가 필요에 따라 관심 해제·재등록하면 새 회차로
등록 알림을 요청할 수 있습니다.

## 설치와 운영

[개인 봇 설치 절차](../teams-app/PERSONAL-BOT-SETUP.md)에 따라 단일 테넌트
Microsoft 앱·Azure Bot을 등록하고 패키지를 생성합니다. 기존 채널 탭 ZIP은
개인 봇을 포함하지 않습니다. 설치용 생성기는 실제 앱 ID와 HTTPS 주소를 받습니다.

`PAI_TEAMS_BOT_APP_ID`, `PAI_TEAMS_BOT_APP_SECRET`, `PAI_TEAMS_TENANT_ID`,
`PAI_TEAMS_PUBLIC_BASE_URL`을 서버에 설정한 뒤 `PAI_TEAMS_FOLLOWUPS_ENABLED=true`로
발송을 켭니다. 설정이 불완전하면 활성화된 발송 서버는 시작되지 않습니다.
로그인을 Teams 탭 안에서 사용할 때는 `PAI_TEAMS_TAB_AUTH_ENABLED=true`도 설정합니다.
추가 DB 테이블은 기존 앱 시작 시 additive migration으로 생성되며 기존 공고를 보존합니다.

API 프로세스가 항상 실행 중인 환경에서는 기본 30초 주기의 내장 워커가 발송합니다.
HTTP 트래픽이 없을 때 잠드는 웹 서비스만으로는 오전 9시 발송을 보장할 수 없습니다.
현재 저장소의 `render.yaml`은 free 웹 서비스이므로 실제 운영 전에 상시 실행 환경을
확보해야 합니다. 이는 선언 파일 확인 결과이며 실제 배포 플랜은 별도로 확인해야 합니다.

상시 실행 서버에서 동일 패키지·DB·봇 환경설정을 사용하는 독립 워커도 실행할 수 있습니다.

```bash
python -m pai_loop.teams_followups --interval 30
# 이미 설정된 운영 스케줄러에서 한 주기만 호출하는 경우:
python -m pai_loop.teams_followups --once
```

독립 워커 전에 앱 배포 또는 `pai-loop-migrate --create-base`로 스키마를 준비합니다.
워커가 여러 개 실행되더라도 동일 DB 큐의 선점으로 중복 처리하지 않습니다.
배포·조직 앱 업로드·봇 개인 설치·실제 메시지 수신은 코드 테스트와 별개로 검증합니다.
이 변경은 발송을 기본 비활성화하며 실제 사용자에게 테스트 메시지를 전송하지 않습니다.

## 검증

```bash
python -m pytest tests/test_teams_bot.py tests/test_teams_followups.py tests/test_teams_cards.py tests/test_teams_tab_auth.py tests/test_teams_followups_frontend.py
node --check src/pai_loop/static/app.js
node --check src/pai_loop/static/login.js
```

테스트는 합성 공고·계정·서명과 격리된 테스트 DB를 사용합니다. 예약 변경,
같은 부서 계정의 개인 분리, CSRF, 잘못된 JWT/테넌트, 동시 선점, 재시도·불명확한
발송 결과, 공개 가능한 카드 정보와 로그인 쿠키 정책을 확인합니다.
