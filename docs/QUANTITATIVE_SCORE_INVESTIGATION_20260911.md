## 2. 해결한 것

### 2.1 정성 항목이 공고 전체를 침몰시키던 문제 — `110a095`

`estimate_quantitative_score`가 이랬다.

```python
statuses = {item.status for item in estimates}
if "REVIEW" in statuses:
    overall = "REVIEW"          # 항목 하나만 REVIEW여도 공고 전체가 보류
```

배점표에는 회사 데이터로 잴 수 있는 행과, 심사위원만 답할 수 있는 행이 섞여 있다.
후자가 REVIEW로 뜨면 **공고 전체가 보류**됐고, 그런 행은 거의 모든 공고에 있으므로
이 규칙 하나가 사실상 모든 추정을 막고 있었다.

`OUT_OF_SCOPE` 상태를 새로 만들어, 그런 행은 범위 하한 0 · 상한 만점으로 두고
준비도·커버리지 분모에서 뺐다. 공고는 `정량 40점 확보, 정성 60점은 만점 가정`으로
읽힌다.

- 지표가 레지스터에 있는 행은 **문구와 무관하게 절대 제외되지 않는다**.
- 전부 정성인 공고는 `UNSCORABLE`로 나간다. 가정 점수만으로 "확정"이라 보고하는 것이
  가장 나쁜 결과이기 때문.
- `OUT_OF_SCOPE`는 항목 전용 상태다. 공유 Literal을 넓혔더니 company fact도 그 값을
  주장할 수 있게 되어, 추정 모델만 별도 타입을 쓰도록 분리했다.

**측정**: 저장된 2,778개 중 801개(29%) 제외 — 가격 290, 정성 267, 총괄·기준선 224,
라벨 추출실패 20. **206개 공고가 정성 때문에 막히던 상태에서 풀렸다.**

### 2.2 배점 칸을 읽지 못하던 문제 — `17adfb7`, `6aa1ff5`, `9afb55b`

`_case_award_matches_literal`이 케이스표의 77%(706개 중 546개)를 막고 있었다.
한국 배점표는 조건과 배점이 **다른 열**에 있는데, 이 술어는 배점이 조건 문구 *안에*
있기를 요구했다.

세 단계로 열었다.

**(a) 눌린 배점 칸** `17adfb7` — PDF 표가 행을 한 줄로 누르면 `C.2~3개교 11`이 된다.
줄바꿈판은 원래 통과했으므로, 셀 경계가 공백으로 바뀐 것뿐인 같은 행이다. 세 가지
증거를 요구한다: 마지막 토큰이 배점 칸으로 읽힐 것, 나머지가 완결된 조건일 것,
**배점값이 조건의 숫자와 겹치지 않을 것**(`A. 7명 이상 7`은 계속 거부).

> 초안이 하드 리턴이라 실패 시 아래의 인라인 경로를 건너뛰었다. 회귀 25건이 났고,
> 성공할 때만 반환하도록 고쳤다.

**(b) 배점이 앞에 오는 표** `6aa1ff5` — `10점 : 5개교 이상`. 순서를 바꾸는 것은
추출 쪽에서 불가능하다. 문구는 인용문의 부분집합이어야 하고 인용문은 원문 그대로여야
하므로, 배점을 앞에 쓴 원문은 **그대로 읽거나 못 읽거나** 둘 중 하나다.

한 행만으로는 열 순서를 증명할 수 없다(기존 `reversed source ownership` 원칙).
증거를 **표에서** 가져왔다: 그 항목의 **모든 행**이 배점으로 시작할 때만 열 순서로
읽는다. 저장된 코퍼스에서 배점-먼저 항목 12개는 전부 모든 행이 같은 모양이었고,
두 순서가 섞인 항목은 하나도 없었다.

가드: 앞 토큰은 점수 단위를 갖고, **뒤에 비교어가 붙으면 안 된다**
(`60%이상`은 기준비율 조건이지 배점이 아니다 — 이건 데이터가 알려줬다).

**(c) 값 겹침 가드 제거** `9afb55b` — 앞자리 분기에서는 표 단위 일관성이 이미 열
순서를 증명하므로, 배점이 임계값과 우연히 같다고 해서 열이 아니게 되지 않는다.
`5점 : 5명 이상`이 이 때문에 거부되고 있었다.

**측정**: 재추출된 공고 기준 배점 관문 통과 0/10 → 7/10 → **10/10**.

## 3. 해결하지 못한 것

### 3.1 (최대 병목) 배점표가 든 첨부를 읽기 전에 예산이 끝난다

**이것이 지금 가장 큰 문제다.** 재추출 19건 중 정량표가 나온 것은 **1건**뿐이었다.
원인은 프롬프트가 아니라 **어느 첨부를 먼저 읽느냐**였다.

측정 (저장된 첨부에서 정량표가 나온 비율):

| 종류 | 첨부 | 표 있음 | 비율 |
|---|---|---|---|
| 제안요청서 | 276 | 262 | **95%** |
| 입찰공고·공고문 | 706 | 187 | 26% |
| 과업지시서·과업내용서 | 127 | 18 | 14% |
| 이름 없는 첨부 | 310 | 36 | 12% |

순번은 약한 신호다(1번 29%, 3번 50%, 5번 17%). 그런데 보강 루프는
`_validated_manifest_attachments()`가 `sort(key=slot)`한 **순번순**으로 읽었다.

19건 중 18건이 매니페스트보다 적게 읽었고, 11건은 레코드에 이유를 직접 적어놨다:

> `배점표는 별도 제안요청서를 참조하도록 되어 있어 확인 불가`

**브랜치에 수정이 있으나 병합·검증되지 않았다** (`e8c7fe6`, `276a2ef`).

예산 구조도 함께 봐야 한다. 마감시각은 진행 중 작업을 죽이지 않고 **다음 것을
시작할지만** 판단하는데, 그 판단이 *이론 최악*을 기준으로 한다.

```
worst_case = 다운로드 12초×3 + Claude 180초×2 + 5초 = 401초
실측       = 중앙 86초 / 최대 219초        ← 5배 차이
```

450초 예산이면 첫 첨부(86초) 후 남은 364초 < 401초라 **두 번째를 시작하지 않는다.**
550초로 올리면 여유가 149초가 되어 중앙값 문서는 2개를 읽는다. 다만 **느린 문서
(219초)는 여전히 1개**다. 219초짜리도 2개 읽으려면 예산 620초가 필요한데 n8n HTTP
타임아웃 600초를 넘는다 — **n8n 워크플로도 함께 고쳐야 가능하다.**

### 3.2 신용등급 3열 표

CREDIT_RATING은 케이스표 최대 집단(222개)인데 배점 관문 통과가 30개(14%)다.
실패 151개를 쪼개면:

- 103개(68%) — 배점 숫자가 문구에 아예 없음 → 재추출이 고칠 대상
- 48개(32%) — 배점은 있으나 조건 문법 불합격

후자가 진짜 다른 문제다. 원문이 `회사채등급 | 기업어음등급 | 대응설명 | 배점`
4열인데 한 문구로 합쳐져서, 범주값을 빼도 `A1`, `①의 …에 준하는 등급`이 남는다.
이는 **범주값이 기업어음 등급을 담고 있지 않다**는 뜻이라, 우리 등급이 A0인 건
맞춰도 CP등급으로 표기된 공고는 못 맞춘다.

   않은 것이었다. 백필 응답에 `ATTACHMENT_CONTINUATION_REQUIRED`가 14건 찍혀 있었다.

5. **"첨부를 못 읽는 오류가 152개(9%)"** — 부풀려진 수치다. `document_processing`
   블록이 없는 다른 종류 레코드까지 실패로 셌다. 진짜 읽기 실패는 4건 정도다.

6. **"콜론으로 열 경계를 판별하자"** — 사용자가 지적한 대로 틀렸다. 진짜 표 셀은
   공백·줄바꿈으로 붙지 콜론이 없다. 표 단위 일관성으로 바꿨다.

7. **"검증기 확장으로 170개가 풀린다"** — 오염된 측정이었다. 비교값(`5~6명`의 5)과
   항목 총점(`(4점)`)을 배점 근거로 잘못 셌다. 조건 바깥으로 한정하니 6개였다.

## 5. 운영 메모

- **`dry_run`도 실제 6시간 리스를 잡는다.** 계획만 보려고 호출하면 그 공고들이 묶여
  LIVE 실행이 0건이 된다. 취소 엔드포인트가 없어 TTL을 기다려야 한다.
- **배치 호출에 `enrich_missing: true`가 없으면** 분석만 돌고 첨부 다운로드·추출이
  일어나지 않는다. W11이 보내는 본문과 맞춰야 한다.
- **CI는 `push: branches:[main]` + `pull_request`**다. 열린 PR 없이 브랜치에 푸시하면
  CI가 돌지 않는다.
- **비용**: 첨부 1개당 약 $0.108 (실측 33개 / $3.57). 시간 예산은 단가를 바꾸지 않고
  요청당 처리량만 정한다. 마감 전 공고의 전체 첨부 1,024개 ≈ $111.
- **로컬 테스트**: 백신이 실행 중 `python.exe`를 삭제한다. 전체 스위트가 42%에서
  반복 사망한 원인이다. `scratchpad/run_suite.sh`가 파일 단위로 나눠 돌리며 복구한다.
  근본 해결은 Windows 보안 제외 항목에 `%APPDATA%\uv` 추가.
