# 유료 호출 없는 정량 원문 재생 조사

2026-09-13. 이번 변경은 원문 파서의 중복을 고치고, 저장된 모델 응답으로 실제 정량 도메인 경로를 반복 검사할 수 있게 한다. 정량 총점 문제가 해결됐다는 보고는 아니다. 신규 모델 호출, 운영 DB 쓰기, 배포는 하지 않았다.

## 조사 범위와 분모

READ ONLY / REPEATABLE READ로 최신 PPS metadata 930공고와 그 whole-manifest에 묶인 추출 세대를 읽었다. 최신 공고 테이블의 상태와 마감 시각으로 실제 마감 전 활성 공고는 288건이었다. 과거의 OPEN 표기나 650건을 현재 실행 대상으로 그대로 사용하면 안 된다.

| 현재 manifest의 첨부 2,865개 | 첨부 수 |
|---|---:|
| 현재 읽기 경로가 선택한 시도 | 177 |
| 정확한 manifest에 시도는 있지만 계약/세대 경계에서 제외 | 1,422 |
| 최신 manifest에 묶인 시도 없음 | 898 |
| 최신 metadata schema 경계가 구형 | 368 |

1,422개는 문서 형식 불지원이 아니다. 최신 header의 prompt 0.5.5가 806개, 0.3.0이 579개, 0.5.0이 37개다. 0.5.5 제외는 정성 행과 근거 없는 배점 추출을 다시 처리하려고 과거 변경에서 의도한 것이다. 이번에는 이를 일괄 허용하지 않았다. 현재 읽을 수 있는 정량 후보는 AVAILABLE 4 / REVIEW 23이다. 저장된 모든 과거 버전을 합산한 후보 수와 구별한다.

기존 19공고와 겹치지 않는 **신규 30공고의 전체 163첨부**를 선정했다. 정상 후보, 현재 정량 실패, 구계약, 무정량 선언, 무시도, 구 metadata를 포함한 의도적 층화 표본이다. 전국 공고의 성공률이나 유병률 추정에 사용할 무작위 표본은 아니다.

- 나라장터의 실제 공개 첨부 161개를 다운로드했다. 2개는 기존 8MB 상한에서 중단했다.
- 현재 운영 파서로 156개를 읽었다. 그중 완전 읽기는 149개이며, 읽기 실패 5개는 HWP 컨테이너 오류 4 / 문자 상한 1이었다. 읽기 성공을 모델 추출 또는 정량 계산 성공으로 세지 않았다.
- 기존 19공고도 원문 문맥을 다시 분류했다. 사용자 예제 3개를 제외한 16개 중 최소 하나의 자체 객관 배점을 확인한 것은 11개, 참조 원문·세부 규칙 미확인은 5개였다. 인용 35개를 원문 offset과 대조했다. 미확인은 정량 비적용이 아니다.

## 확인하고 고친 원인: HWPX 표의 중복 전사

기존 HWPX 파서는 모든 `hp:p`에서 자손 `hp:t`를 모았다. 표를 품은 상위 문단이 셀 문단의 내용까지 이어 붙인 다음, 각 셀 문단을 방문하면서 같은 XML 문자 노드를 다시 읽었다. 문자열이 우연히 같다는 추측이 아니라 **동일 XML 노드가 여러 문단의 자손으로 소비되는 것**을 확인했다.

신규 30공고 중 14공고/31첨부에서 발생했다. 이 파일들의 입력은 **503,694 → 412,392자**, 91,302자(약 18.1%) 줄었다. 전체 163첨부에서 읽힌 모델 입력 합계는 2,267,694 → 2,176,392자였다. 토큰 수·모델 정확도·달러 절감률을 실측한 값은 아니다.

수정은 XML을 원래 순서대로 한 번 방문해 문단의 소유 문자만 출력한다. 같은 점수가 다른 셀에 반복되는 경우는 그대로 남긴다. 표 앞뒤 문장, 중첩 표, 각주, 여러 run으로 나뉜 단어와 최소 형식의 직접 문단 문자도 보존한다. 깊은 XML을 Python 재귀로 방문하지 않으며 누적 문자 상한을 문단 수집 중 검사한다.

별도 검증에서 실제 HWPX **33개, 고유 `hp:t` 비공백 문자 324,571자**의 내용과 순서가 모두 보존됐다. 변경 파일은 중복이 있던 31개이며 다른 형식의 canonical은 달라지지 않았다. 이 검증은 표의 의미나 회사 점수까지 보증하지 않는다.

새 쓰기 처리버전은 0.5.2다. 직전 0.5.1의 정확한 prompt/schema/validator 조합과 기존 0.5.6·0.5.4 읽기를 보존한다. 0.5.1은 최신 CASE 구간/미제출 표현을 그대로 읽는다. 새 처리 세대가 생긴 뒤 더 옛 성공으로 되돌아가지는 않는다. 실제 전체 snapshot에서 **선택 177개와 정확한 version ID 집합, AVAILABLE 4 / REVIEW 23이 모두 유지**됐다. 원본 record·fingerprint를 고쳐 붙이지 않았다.

파서 수정으로 old canonical을 재현할 수 없으면 기존 source revalidation은 DIAGNOSTIC_ONLY를 유지한다. source/input hash가 모두 같은 기존 중복 결과의 무료 재사용 경로는 보존하고, 달라진 입력을 동일한 것으로 취급하지 않는다.

## 비용을 줄이려면 무엇을 제외해야 하는가

파일명이나 `정성` 단어로 문서 전체를 제외하면 실제 배점을 놓친다. 신규 표본 R26BK01726177의 **과업지시서.pdf 10~11쪽**을 화면과 canonical 양쪽에서 확인했다. 정량은 신용평가 10점이고, 같은 표의 유사사업 실적은 정성 영역이다. 최근 3년·5천만원이라는 숫자가 있다는 사실만으로 후자를 자동 정량 함수로 바꿀 수 없다.

원문에는 서로 다른 신용수단의 평점 중 높은 값을 쓰는 조건도 있다. 다른 문서의 최신 등급 다수 시 낮은 등급을 쓰는 조건과 동일하지 않다. 유사 IBK 서식끼리도 실제 배점이 달랐다. 기관명, 서식 모양, 등급 문자열 유사성만으로 규칙을 복사하지 않는다.

따라서 다음의 순서가 필요하다.

1. 이미 받은 원문과 저장 응답을 재사용한다. 파서/계약/검증기 문제는 먼저 아래 로컬 재생으로 검사한다.
2. 정량 기준과 그 적용 문장·각주·참조 서식을 한 묶음으로 검토한다. 물리적 표가 없는 감점 문장도 확인한다. 계약 일반조건·정성 설명을 줄이려면 적용 참조가 없는 범위인지 먼저 검토해야 한다.
3. 참조한 제안요청서나 외부 기준 본문이 없으면 먼저 원문을 확보한다. 같은 불완전 입력을 다시 모델에 보내도 누락된 원문을 만들 수 없다.
4. 실제 배점/인정조건이 확보됐는데 저장 raw에 누락·오독이 있는 경우만 별도 추출 문제로 남긴다. 버전 차이와 내용 오류를 섞어 전체를 유료 재실행 대상으로 삼지 않는다.

이번 변경은 자동 페이지 삭제나 정량 비적용 분류기를 도입하지 않는다. 그런 삭제의 재현율을 원문 대조 없이 주장하지 않는다.

## 실제 계산 경로의 무료 재생

`scripts/replay-quantitative-sources.py`는 로컬 snapshot과 source-map을 명시적으로 받는다. 데이터 수집용 DB 접속이나 나라장터 다운로드는 이 실행기에 포함되지 않는다.

```text
python scripts/replay-quantitative-sources.py --snapshot snapshot.json --source-map source-map.json --output replay.json
```

선택적으로 `--company-snapshot company.json`을 지정할 수 있다. `snapshot`에는 notices/versions의 실제 컬럼을, `source-map`에는 sources 배열의 version_id/native_path/canonical_path/native_sha256/canonical_sha256을 준다. 기존 출력 파일은 덮어쓰지 않는다. 원문·회사자료·결과는 private 경로에 둔다.

실제 source selector → source parse → 요구사항 merge → 현재 manifest 증명 merge → 규칙 compile → `estimate_for_notice`를 호출한다. DB SELECT 한 종류만 고정된 메모리 행으로 공급한다. provider, socket, DB 연결/쓰기, subprocess 호출은 예외로 차단한다. 운영 lease·저장 transaction·API 화면까지 수행한 end-to-end 시험은 아니다.

원문 재생에는 두 갈래가 있다. 저장 계약으로 읽는 계산 경로와, 정확한 native bytes에 저장 raw를 대조하는 후보 진단이다. 구계약 raw도 현재 스키마로 읽을 수 있으면 현재 실제 파서/후보 검증기에 넣되 원계약을 보존한다. 진단 profile을 저장 증명이나 회사 점수 입력으로 주입하지 않는다.

30공고의 저장 경로는 수정 전후 규칙 활성화 1 / REVIEW 29였다. 사용한 회사자료는 fact ID·증빙 link 일부가 생략된 기존 frozen 부분집합이므로, 이 재생에서 확정 총점 0이라는 결과는 **운영 DB에 증빙이 없거나 실제 회사가 0점이라는 뜻이 아니다.** 이 결과로 전체 문제가 해결됐다고 주장할 수 없다.

원문 bytes와 저장 raw를 직접 대조할 수 있었던 90첨부 중 raw가 정량 묶음을 선언한 것은 25첨부/78항목이었다. 현재 후보 검증 결과는 파서 수정 전후 모두 **AVAILABLE 3 / REVIEW 75**다. 중복 전사를 고쳐도 이미 누락·오독된 저장 응답의 내용까지 저절로 복구되지는 않았다. 이 25개는 raw의 선언 개수이며 원문 전체의 실제 배점 존재율은 아니다.

같은 첨부에서 같은 원인을 여러 번 세지 않으면 주요 차단은 추출기의 누락 선언 51첨부, metric/evidence 불완전 각 15, 최대배점 literal 불일치 14, 평가항목 literal 불일치 12, CASE 숫자 불일치 10이다. 이들은 중첩 원인이다. 나머지 16시도는 구 스키마를 읽지 못한 것이 아니라 `result=null`이었다: HTTP 오류 11, 인용 거절 3, 스키마 검증 거절 1, 빈 문서 1. 저장 응답 자체가 없는 경우와 저장 내용이 틀린 경우를 분리했다.

원문 누락, 잘못 묶인 소계·정성 행, 배점/비교값 오독, 인정조건 누락을 수정해야 할 대상으로 유지한다. 원문이 없는 경우와 원문은 있는데 저장 응답이 틀린 경우를 분리한 재생 결과를 다음 수정의 기준으로 사용한다.

## 검증 및 재현 자료

새 파서 회귀는 중첩 셀, 동일 점수 반복, run 결합, 부모 앞뒤, 각주, 직접 문자, 문단 밖 메타데이터, 깊이 1,100, 누적 문자 상한을 검사한다. 처리 계약 회귀는 기존 읽기, BETWEEN/NOT_SUBMITTED, 혼합 버전 거절, 새 세대 차단, 무료 재사용의 hash 경계를 검사한다. 재생 CLI는 SYN 회사 점수 계산과 네트워크/provider/DB 차단, 원본 불변, 진단 결과의 비승격을 검사한다.

서로 겹치지 않는 집중 묶음 **995개 통과**: 파서·정량 계산·PPS·공개 점수 경로 605, 계약 호환·파이프라인 377, 재생 CLI 13. 별도 기존 native adapter 22개도 통과했다. 전체 CI/coverage gate를 새 커밋으로 실행한 결과는 아니며, 운영 배포·화면 반영 검증도 이번 범위에 없다.

private 원문과 DB snapshot은 Git에 넣지 않는다. 로컬 `.local/broad-quantitative-audit/`의 `census_report.md`, `download_inventory.private.json`, `parsed_before.private.json`, `parsed_after.private.json`, `parser_delta.private.json`, `hwpx_whole_node_sequence.private.json`, `source_labels_19.private.json`, `pdf_control_review.private.json`, `processing_read_preservation.private.json`, `final_offline_replay_v2.private.json`, `replay_findings.md`가 측정 근거다.
