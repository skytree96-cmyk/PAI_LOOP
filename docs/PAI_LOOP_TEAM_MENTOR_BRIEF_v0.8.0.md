## 공유용 요약

[워크플로우 아키텍처 한눈에 보기](architecture/PAI_LOOP_workflow_architecture_v1.6.png)

**현재:** **[FACT]** PAI LOOP는 조달청 실공고와 첨부문서를 읽고, 회사 증빙과 대조한 참가자격·정량 준비도·3년 낙찰/가격 리스크를 근거와 함께 웹에 보여주는 입찰 사전검토 시스템이다. Render 웹, PostgreSQL, 매일 09:00 n8n이 연결돼 있으며 Teams는 회사 승인 전 mock이다.

**백필 결과:** **[FACT]** 기존 미분석 89건은 `89/89` 처리됐고 실패·잔여는 0건이다. 2026-08-17 진행 공고 100건의 공개 사유는 `ANALYZED 35 / QUOTE_UNVERIFIED 56 / ATTACHMENT_NONE 3 / HWP_ONLY_UNSUPPORTED 2 / HWPX_EXTRACT_FAILED 1 / PDF_EXTRACT_FAILED 2 / OPENAI_REVIEW 1 / NOT_SELECTED 0`이다. 원문 인용을 확인하지 못한 건은 PASS로 올리지 않고 REVIEW로 남겼다.

**데모 5단계:** `① 실공고 수집 → ② 부서별 우선순위 → ③ 원문 근거 PASS/REVIEW/FAIL → ④ 정량점수·3년 낙찰/가격 참고 → ⑤ 사람 결정·결과 DB 환류` 순서로 보여준다.

**완료 1 + 다음 수정 Top 4**

1. **[FACT / 완료]** 미분석 89건을 일회성 전량 처리했고, 이후 매일 신규·변경 공고 전량을 우선 분석하는 재개 가능한 큐를 운영한다.
2. **[TARGET]** 신규 공고의 정량 배점표·산식을 자동 추출하되 사람 승인 후 계산 규칙으로 승격한다.
3. **[TARGET]** 구형 binary HWP를 격리 변환하고 표·페이지/셀 근거 품질 Gate를 적용한다.
4. **[TARGET]** 23건 정답셋 회귀와 R01~R07·R09 예외 승인·재판정 흐름을 현업 검수한다.
5. **[TARGET]** 유사사업·가격 비교군을 고도화하고, 회사 승인 후 Teams 실제 알림·SSO/RBAC을 연결한다.

**멘토에게 우선 물을 3가지**

1. 공모전의 1순위 KPI를 공고 누락률, 판정 정확도, 근거 설명력, 검토시간 절감 중 무엇으로 둘 것인가?
2. “신규 전량”의 관련도 하한과 폭증일 비용·완료시간 상한을 어떻게 정할 것인가?
3. 자동 추출한 정량표와 3년 유사사업 비교군을 언제 신뢰 가능한 결과로 인정할 것인가?

> 핵심 한계: 자동 투찰·자율 ML 학습이 아니며, Teams 실제 전송·신규 공고 정량표 일반화·binary HWP 처리는 아직 완료되지 않았다. 낙찰·가격 수치는 담당자 검토용 예측이다.

## 부록 A. 현재 한 줄 정의

**[FACT]** PAI LOOP는 나라장터 공고와 첨부문서를 수집·구조화하고, 공고 마감일 기준 회사 증빙과 대조해 참가자격, 정량 준비도, 경쟁·가격 리스크를 근거와 함께 제시한 뒤 사람이 최종 입찰 여부를 결정하도록 돕는 시스템이다.

자동 투찰 도구가 아니며, 초기 환류는 자율 ML 학습이 아니라 **사람 검수·실제 결과·규칙 버전을 축적해 승인된 규칙과 임계값을 개선하는 과정**이다.

## 부록 B. 데모에서 보여줄 5단계

1. **실공고 수집** — **[FACT]** n8n이 조달청 입찰공고 API를 호출하고 `교육·컨설팅 + 24개 부서 키워드`로 신규 공고를 수집·중복 제거한다.
2. **부서별 후보 선별** — **[FACT]** 웹에서 검색 주체 부서와 추가 키워드에 따라 공고 우선순위와 추천 근거가 달라지는 모습을 보여준다. 기본 정렬은 `PASS → REVIEW → 미분석/오류 → FAIL`이다.
3. **근거 기반 판정** — **[FACT]** 실제 PDF/HWPX의 자격조건과 원문 인용을 보여주고, 회사 공개 증빙과 비교한 `PASS / REVIEW / FAIL` 및 필요한 행동·체크리스트를 설명한다.
4. **정량·낙찰 인텔리전스** — **[FACT]** 검수 완료된 배점표의 점수 범위와 증빙 공백, 최근 3년 유사 낙찰 후보의 반복 수주사·낙찰률·경쟁집중도·가격 참고범위를 함께 보여준다.
5. **결정과 환류** — **[FACT]** 분석 snapshot과 실제 `NO_BID / SUBMITTED / WON / LOST` 결과를 온라인 DB에 보존하는 구조를 설명한다. Teams는 실제 전송 대신 동일 내용을 보여주는 Adaptive Card mock으로 시연한다.

데모는 새 API 호출의 성공 여부에 의존하기보다, 처리 완료된 진행 공고에서 근거가 풍부한 `PASS 1건 + REVIEW 1건 + 문서 제한 1건`을 고정 시나리오로 선정한다.

## 부록 C. 현재 구현된 것

- **[FACT] 공고 발견:** 조달청 실공고 bounded 수집, 변경·취소·재공고 처리, 부서 키워드 기반 우선순위가 구현돼 있다.
- **[FACT] 문서 분석:** PDF와 HWPX 본문 추출, OpenAI strict-schema 구조화, 원문 인용 재검증, 실패 사유 분류가 구현돼 있다.
- **[FACT] 판단:** 참가자격과 정량 준비도를 분리하고, `PASS → 연결 REVIEW → DF-000 DEFAULT FAIL`의 결정론적 판정 경계를 갖는다.
- **[FACT] 실제 데이터:** 공개 실적 1,182건, 낙찰 이력 59건, 실제 인천 공고 요구조건 23건 및 근거 anchor 26건이 검토용 데이터로 연결돼 있다.
- **[FACT] 정량·경쟁:** 한 개의 검수된 실제 RFP에 대해 20점 배점표 기반 점수 범위를 제공하고, 저장된 3년 유사 낙찰 후보로 수주 집중도·낙찰률·가격 참고범위를 계산한다.
- **[FACT] 온라인 DB:** 관리형 PostgreSQL에 판단 기준 버전, 분석 run, 조건·점수·추천 snapshot, 실제 입찰 결과를 분리 저장하며 과거 snapshot을 덮어쓰지 않는다.
- **[FACT] 운영 채널:** Render 웹과 매일 09:00 KST n8n 통합 워크플로가 연결돼 있다. Teams는 회사 승인 전까지 mock-only다.
- **[FACT] 분석 적체 해소:** `NOT_SELECTED` 89건을 재개 가능한 3개 구간으로 전량 처리했다. n8n 감사 합계는 계획 89·시도 89·완료 89·실패 0·잔여 0이며, 이후에는 당일 신규·변경 공고를 우선 전량 분석하고 재시도 대상은 cooldown이 있는 bounded 순환 큐로 처리한다.

## 부록 D. 기획안 대비 다음 수정 우선순위

### P0 — 데모 신뢰성과 핵심 기능

1. **신규 전량 분석 운영 관찰** — **[FACT]** 89건 backfill과 매일 신규·변경 전량 분석에 재개 지점, 중복 방지, 비용 추정용 API 호출량·처리시간 기록, 부분 실패 재시도를 적용했다. **[TARGET]** 폭증일 완료시간, REVIEW 재시도율, 호출비용, dead-letter를 운영 KPI로 관찰한다.
2. **신규 공고 정량표 일반화** — **[TARGET]** 현재 한 개 실공고에 수동 검수된 정량 프로필을 신규 공고에도 확대한다. LLM은 배점표·산식·근거 후보를 추출하고, 사람 승인 후에만 규칙 버전으로 승격해 계산한다.
3. **구형 HWP 운영 경로** — **[TARGET]** binary HWP를 격리된 한컴 변환 워커에서 HWPX/PDF로 변환하고 표·페이지/셀 anchor 품질 Gate를 통과시킨다. 변환 실패는 R07 REVIEW로 유지한다.

### P1 — 판단 품질과 결과 환류

4. **23건 정답셋 회귀 및 현업 라벨 승인** — **[TARGET]** 기획안의 23개 실공고를 조건 단위로 재현하고, 초기 엔진판정과 현업 최종정답을 분리해 오류 유형과 KPI를 측정한다.
5. **예외 승인·재판정 화면** — **[TARGET]** R01~R07·R09 질의, A/B/BLOCKED 근거등급, 승인자·유효기한·무효조건을 웹에서 기록하고 해당 공고·조건에만 재판정한다.
6. **유사사업·가격 예측 고도화** — **[TARGET]** 제목 유사도 외에 발주기관, 사업 범위, 평가방식, 기간, 금액을 반영해 3년 비교군의 신뢰도를 높인다. 회사 원가·최소마진을 반영한 최종 투찰가는 별도 재무 승인 영역으로 둔다.

### P2 — 사내 운영 전환

7. **Teams 실제 연결과 사내 권한** — **[TARGET]** 회사 승인 후 Teams 실제 알림, 웹 진입 링크 또는 탭, Entra SSO와 `viewer/reviewer/approver/admin` 권한을 연결한다.
8. **운영 품질 관리** — **[TARGET]** API 호출량·비용, schema drift, dead-letter, 분석 누락, 09:00 완료시간, 근거 없는 PASS 0건을 모니터링하고 DB backup/restore 및 객체 저장소 보존정책을 검증한다.

## 부록 E. 멘토에게 물을 결정 질문 5개

1. **공모전의 1순위 성과지표는 무엇인가?** 공고 누락률, 판정 정확도, 근거 설명력, 검토시간 절감 중 어떤 지표를 앞세울지 결정이 필요하다.
2. **매일 “신규 전량”의 운영 경계는 어디까지인가?** 조직 키워드 적중 공고를 모두 분석할지, 관련도 하한을 둘지, 폭증일의 비용·완료시간 상한을 어떻게 둘지 의견이 필요하다.
3. **자동 추출된 정량 배점표를 언제 계산 가능 상태로 인정할 것인가?** 원문 anchor 100%, 합계 검증, 사람 1인 승인 등 최소 승격 Gate를 정해야 한다.
4. **3년 낙찰 비교군을 ‘유사사업’으로 인정할 기준은 무엇인가?** 제목·기관·과업·평가방식·예산 중 필수 조건과 최소 표본 수를 정해야 가격 예측을 과장하지 않을 수 있다.
5. **사내 파일럿의 실제 사용 채널과 승인자는 누구인가?** 웹 중심+Teams 알림으로 시작할지, Teams 탭까지 포함할지와 예외·GO 결정의 책임자를 확정해야 한다.

## 부록 F. 주의와 현재 한계

- **[FACT] Teams는 mock이다.** 실제 전송·탭·SSO는 회사 승인과 credential 설정 전에는 작동하지 않는다.
- **[FACT] 정량점수 자동화는 아직 일반화되지 않았다.** 신규 공고에서 배점표를 발견해도 자동으로 확정점수를 만들지 않으며, 현재는 한 개의 검수된 실제 RFP 프로필만 계산 가능하다.
- **[FACT] 구형 binary HWP는 온라인 분석 제한이 있다.** PDF/HWPX는 처리하지만 HWP만 있는 공고는 안전하게 REVIEW로 남긴다.
- **[FACT] 낙찰·가격 결과는 검토용 예측이다.** 제목 유사 후보가 동일 사업 또는 독점시장을 뜻하지 않으며, 예정가격·투찰금액·평가점수가 없는 값은 추정으로 채우지 않는다.
- **[FACT] “학습용 DB”는 자동학습 모델이 아니다.** 판단 완료 snapshot, 사람 수정, 참여·낙찰·실주 결과를 축적하고, 승인·회귀검증을 거친 규칙/임계값 개선에 사용한다.
- **[FACT] 89건 backfill은 3개 구간·30개 child job으로 완료됐고 OpenAI 호출은 86회였다.** **[TARGET]** 원문 인용 검증 REVIEW가 다수이므로 PASS·REVIEW·문서 제한 표본을 사람이 검수한 뒤 데모 대표 사례를 확정해야 한다.
- **[FACT] 7일 보관은 단기 운영로그에만 적용한다.** 판단 기준 버전, 분석 snapshot, 낙찰·입찰 결과는 재현과 환류를 위해 장기 유지한다.
- **[FACT] PAI LOOP의 출력은 법률판단이나 자동 투찰 명령이 아니다.** 최종 참가·가격·제출 결정은 담당자가 원문과 최신 증빙을 확인하고 승인한다.

## 부록 G. 팀 피드백 요청

데모 확인 후 각 팀원은 아래 세 가지만 남긴다.

1. 실제로 검토하고 싶은 공고가 상단에 올라오는가?
2. `PASS / REVIEW / FAIL`과 정량·가격 근거가 결정에 충분한가?
3. 아침 알림에서 반드시 보여야 할 정보 한 가지와 빼도 될 정보 한 가지는 무엇인가?
