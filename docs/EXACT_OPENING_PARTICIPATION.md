# 같은 개찰 회차의 실제 참여 확인과 자동 결과

기존 결과 환류에 선택적인 참여 업체 조회를 연결한다. 우리 회사가 같은 개찰
회차의 업체 목록에 정확히 식별되면, 수기 SUBMITTED 기록이 없어도 최종 낙찰자와
비교하여 WON 또는 LOST를 기록할 수 있다. 옵션은 기본 비활성이다.

## 기존 운영 경로

서버 인증이 필요한 기존 `POST /api/v1/outcome-feedback/pps/refresh`를 사용한다.
브라우저 계정·PIN의 권한을 추가하지 않으며 W10 운영 설정도 이 변경에서
활성화하지 않는다. 기존 W10 또는 승인된 서버 작업에서 다음 옵션을 명시한다.

```json
{
  "notice_keys": ["PPS-SYN-EXACT-PARTICIPATION"],
  "max_notices": 10,
  "max_pages_per_notice": 1,
  "include_participation": true,
  "participation_max_pages": 1,
  "dry_run": true
}
```

`notice_keys`를 생략하면 기존 최근 종료 공고 선택·순환 규칙을 사용한다.
`include_participation`은 기본 false, `participation_max_pages`는 기본 1/최대 2다.
한 페이지는 100행이며 기존 75초 작업 제한을 최종낙찰과 참여 조회가 공유한다.
추가 조회는 선택된 공고의 정확한 회차에만 수행하며 날짜 전체 재탐색이나 새
작업 트리거를 만들지 않는다. 항목 및 전체 `api_calls`에 두 조회를 모두 합산한다.
`dry_run: true`도 공급자 조회와 감사 작업 기록은 수행하지만 결과는 저장하지
않는다. `dry_run: false`가 실제 결과 저장이다. 실제 활성화·실행은 운영자가 한다.

## 판정 계약

최종낙찰: `getScsbidListSttusServcPPSSrch`

참여 업체: 기존 공통 클라이언트의 `getOpengResultListInfoOpengCompt`

### 최종낙찰의 정확번호 조회

공식 [낙찰정보서비스의 참고문서 1.1](https://www.data.go.kr/data/15129397/openapi.do)
(`조달청_OpenAPI참고자료_나라장터_낙찰정보서비스_1.1.docx`, 2026-09-08 확인)의
각 용역 오퍼레이션 요청 메시지 표에 따라 단건 어댑터는 다음 두 경로만 허용한다.

| 최종낙찰 오퍼레이션 | 공고번호 조회 `inqryDiv` |
| --- | --- |
| `as/ScsbidInfoService/getScsbidListSttusServcPPSSrch` | `3` |
| `as/ScsbidInfoService/getScsbidListSttusServc` | `4` |

PPSSrch의 `1`은 공고게시일시, `2`는 개찰일시 검색이다. 번호를 추가하더라도
날짜 검색 모드를 정확번호 검색으로 취급하지 않는다. 기본 용역 오퍼레이션은
조회구분 체계가 다르므로 같은 숫자를 재사용하지 않는다. 알 수 없는 경로는
공급자 호출 전에 거부한다.

기본 경로의 단건 요청 조건은 다음과 같다. 공통 클라이언트가 서버 인증과
JSON 응답 형식을 적용하며, 다른 기관·회사·날짜 필터는 추가하지 않는다.

```json
{"inqryDiv":"3","bidNtceNo":"SYN-EXACT-NUMBER","pageNo":1,"numOfRows":100}
```

번호 조회는 날짜 구간마다 반복하지 않고 공고당 한 번의 페이지 순회만 수행한다.
기존 `start`/`end`/`max_window_days` 인자는 호출 호환성과 입력 검증을 위해 남지만
번호 조회의 공급자 필터나 반복 횟수를 결정하지 않는다. 공고 선택용 최근 기간,
역사 낙찰·회사 낙찰의 날짜 탐색, 전역 오퍼레이션 설정은 그대로다. 성공 항목의
조회 방식 경고는 `QUERY_MODE_NOTICE_NUMBER`이며 이전 `QUERY_WINDOW_BASIS_*`를
현재 공급자 조회 조건으로 표시하지 않는다.

최종낙찰 요청표에는 공고차수·분류·재입찰 검색 조건이 없으므로 이를 공급자가
필터링했다고 가정하지 않는다. 반환된 번호와 차수를 다시 대조하고, 아래 네 키의
명시성·일치성과 전체 페이지 검증을 유지한다. 공급자가 번호 조건을 무시하거나
페이지 제한에 도달하면 기존 REVIEW/부분 응답 처리로 남는다. 요청 방식 수정은
실제 특정 공고의 낙찰·참여 데이터 존재나 운영 조회 성공을 증명하지 않는다.

| 내부 키 | 공급자 키 |
| --- | --- |
| bid_notice_no | bidNtceNo |
| revision_no | bidNtceOrd |
| classification_no | bidClsfcNo |
| rebid_no | rbidNo |

네 값이 모두 명시되고 동일해야 한다. 숫자 차수의 앞자리 0만 정규화하며, 누락이나
빈 값을 0으로 보완하지 않는다. 업체 목록의 건수·페이지·중복·회차와 최종낙찰의
단일 회차/행을 검증한다. 최종결과의 참여 업체 수가 있으면 목록 건수와도 대조한다.
모든 업체 식별자가 유효해야 하며, 우리 회사와 최종 낙찰자가 같은 목록에서 각각
정확하게 식별되어야 한다. 두 업체가 같으면 WON, 다르면 LOST다. 개찰순위 1위,
업체명 유사도, 수기 회차 입력만으로 판정하지 않는다.

회사번호는 기존 승인된 회사 조회 상수를 사용하고 [KMA 공식 회사소개](https://www.kma.or.kr/kr/usrs/eduRegMgnt/eduRegMgntForm.do?cateNm=abtKma)
공개 정보와 대조했다(2026-09-08). 현재 공개 프로필의 번호 제외 정책을 유지한다.
[조달청 공식 낙찰정보서비스](https://www.data.go.kr/data/15129397/openapi.do)는 최종낙찰자와
개찰순위를 제공한다. 동적 상세 명세에서 확인되지 않거나 응답에 누락된 식별
필드는 추정하지 않는다. `prcbdrBizno`가 없거나 마스킹되면 참여 확인은 REVIEW다.

회차 혼합·업체/낙찰자 불일치·중복·부분 페이지·시간 초과·자기 회사 부재는 REVIEW다.
최종낙찰 자체가 아직 없으면 기존 NO_RESULT 상태를 유지한다. 업체 목록에 없다는
사실은 NO_BID 또는 미참여의 확정 근거가 아니며 NO_BID를 자동 생성하지 않는다.
공동수급 대표사만 공개되거나 특정 업무의 업체 식별이 제공되지 않으면 이 경로로
자동 판정할 수 없다. 제공되지 않은 투찰률·점수·실주 사유를 추정하지 않는다.

## 소유권과 감사

- 원본 번호는 클라이언트 내부에서만 비교하고 반환·저장하지 않는다. 참여 증명에는
  source kind, 일치/완전성 boolean, 네 개찰 키, 공개 출처, 정규화된 사실의 digest를
  남긴다. 회사번호 해시·담당자·연락처·원본 응답은 남기지 않는다.
- `PROVIDER_PARTICIPANT_EXACT`는 서버 전용 `PPS_AUTO_FEEDBACK` 소유 기록에서만
  인정한다. 결과 편집 payload는 source/evidence/proof/참여 확인 boolean을 받지 않는다.
  일반 결과 API도 자동 결과 namespace를 생성·변경할 수 없다.
- 자동 결과는 회사 전체 관측이며 계정·부서·수기 판단 ID를 배정하지 않는다.
  기존 사람 판단, 부서별 CAS, 투찰률 및 회차 변경 이력은 유지한다.
- 공급자 호출 후 짧은 쓰기 transaction에서 공고 유효성, 최신 사람 검토와 최신
  자동 관측을 다시 읽는다. 같은 회차의 최신 NO_BID/CANCELLED/미검증 정정 또는
  상충하는 최종결과는 자동으로 덮지 않는다. 늦게 도착한 이전 공급자 요청은
  더 최신에 저장된 결과를 덮지 않는다.
- 수기 생성·수정, 기존 서버 전용 MANUAL 결과 저장과 자동 결과는 같은 공고의 transaction 잠금을 공유한다.
  PostgreSQL에서 사람 검토 재조회와 자동 저장 사이에 수기 정정이 끼어들 수 없다.
  수기 생성은 기존 부서 잠금 이후 공고 잠금을 얻으며 부서 CAS를 계속 확인한다.
  수정은 잠금 전 읽기를 버리고 잠금을 얻은 뒤 소유권과 버전을 다시 확인한다.
  옵션을 보내지 않는 기존 W10 호출도 자동 저장 전 동일한 잠금을 얻고 최신
  증명과 수기 참여 근거를 다시 읽는다. 증명 확인과 UPDATE 사이에 새 참여
  증명이 끼어들어 기존 호출에 의해 사라지는 경쟁을 허용하지 않는다.
- 반복된 동일 관측은 UNCHANGED이며 공급자 사실 변경 시 이전 증명을 이력에
  남긴다. 옵션을 보내지 않는 기존 호출은 새 참여 증명과 투찰 사실을 지우지 않는다.
  기존 수기 참여 근거와 회차 미확인 legacy 결과의 검토 상태도 보존한다.

## 결과 화면

결과 카드에 서버의 참여 확인 여부와 회차를 표시한다. 편집창에는 공고번호·차수를
읽기 전용으로 표시하고, 확인한 분류번호·재입찰번호를 함께 입력하거나 둘 다 비울
수 있다. 자동 결과의 검토본은 회차 및 기준 원본 참조를 보존하지만 스스로 공급자
참여 증명을 소유하지 않는다. 기존 클라이언트가 검토본 생성에서 회차를 생략하면
기준 원본의 유효한 회차를 상속한다. 명시적인 null은 회차 미확인으로 저장한다.
회차 입력 오류는 두 입력칸의 input/change에서 다시 검사하므로 값을 고친 뒤
브라우저 자체 제출 검증이 이전 오류 때문에 저장을 계속 막지 않는다.

외부 참여 조회를 시작하는 새 UI 버튼은 없다. 기존 목록 새로고침은 저장된 결과를
읽는다. 운영 측에서 위 옵션으로 환류를 실행한 뒤 목록에서 확인한다. 현장 단말과
실제 공급자 응답으로 검증하는 작업은 이 구현의 합성 테스트와 별개다.
