# 부서 로그인 전환 운영 안내

이 변경은 코드 준비이며 실제 활성화·로그인 검증·운영 배포를 실행하지 않는다. PIN 입력창과 브라우저 PIN 인증은 폐기한다. 서버 간 n8n API key, 기존 워크플로, 계정 비밀번호·역할·유료 권한은 바꾸지 않는다.

## 초기 관리자 활성화

기존 등록은 신규 계정만 생성하므로 비활성 관리자를 다시 bootstrap해도 활성화되지 않는다. 다음 경로는 이 최초 활성화만 해결한다. 원본 등록 계획이나 비밀번호를 다시 전송할 필요가 없다.

1. 새 서버 코드의 CI·배포를 확인한다. `PAI_LOOP_DEPARTMENT_ACCOUNTS_ENABLED`의 현재 상태를 확인한다. 아래 서버 전용 경로는 flag가 꺼져 있어도 사용할 수 있다.
2. 승인된 내부 n8n UI에서 **기존 Backend credential**을 선택해 `POST /api/v1/accounts/initial-admin-activation`에 아래 preview 본문을 한 번 전송한다. 브라우저 JS에 서버 키를 넣지 않는다. HTTP 노드는 자동 재시도 없이 사용하고 새 트리거나 예약을 만들지 않는다.
3. `WOULD_ACTIVATE`와 대상 ADMIN·department 없음·inactive·paid false·revision 1을 확인한다. 다른 계정이나 상태이면 중단한다. 실제 등록 ID는 운영자가 별도 승인 자료에서 확인한다.
4. 동일 대상과 응답의 preview ID로 apply를 한 번 실행한다. `ACTIVATED`를 확인한다. preview는 15분·일회용이며 현재 DB 상태에 HMAC으로 묶인다. 비밀번호, 역할, paid grant는 변경하지 않는다.
5. 응답 유실/타임아웃/409이면 **apply를 재전송하지 않는다**. 새 dry run으로 상태만 읽는다. `ALREADY_ACTIVE`는 새 활성화가 아니라 현재 상태 확인이다. 비활성·변경·불명확이면 원인을 확인한 뒤 별도 판단한다.

합성 예시(실제 등록 ID나 비밀번호가 아님):

```json
{"username":"SYN_ADMIN","dry_run":true}
```

```json
{"username":"SYN_ADMIN","dry_run":false,"preview_id":"SYN-preview-from-response"}
```

이 경로는 활성 관리자가 0명인 때의 **수정되지 않은 초기 ADMIN**에 한정한다. 기존 비밀번호 분실이나 의도적으로 비활성화한 관리자 복구, 일반 계정 변경 기능이 아니다. 등록 preview를 활성화에 재사용할 수 없다. 현재 계정 트랜잭션 잠금과 preview 저장소를 재사용하며 새 migration은 없다.

## 브라우저 로그인 검증과 부서 활성화

1. account flag를 활성화하고 업무앱의 **부서 로그인**에서 초기 관리자로 로그인한다. `/accounts/me`의 ADMIN·manage_accounts=true·paid=false를 확인한다. 소스 변경만으로 로그인 성공을 간주하지 않는다.
2. 계정 창의 **부서 계정 활성화**에서 발급 대상과 상태를 확인한다. 승인된 부서별로 활성화한다. UI는 기존 `PATCH /accounts/{id}`에 `{expected_revision,active:true}`만 보낸다. 역할·비밀번호·유료 권한은 보내지 않는다. 동시 변경은 409로 거절되며 불명확한 결과는 새로고침으로 확인한다.
3. 최소 한 부서의 실제 로그인을 운영자가 확인한다. 타 부서 판단·결과 조회, 자기 부서만 작성, 관리자 대리 판단 금지, stale CAS 거절을 확인한다. 사용자는 다른 부서로 작업할 때 로그아웃 후 해당 계정으로 로그인한다.
4. 나머지 활성 상태를 다시 조회한다. 신규 계정 생성이나 임시 비밀번호 이메일 발송은 이 작업에 포함되지 않는다.

서버의 기존 세션 hash에 버전 구분을 추가하여 이전 앱에서 발급한 쿠키는 새 앱에서 재로그인이 필요하다. 초기 관리자 활성화는 저장된 모든 미취소 세션도 취소한다. 이후 부서 활성화/일반 관리자 PATCH는 해당 계정 세션을 취소한다. 성공 로그인은 기존 실패 시도 예산을 지우거나 추가 소모하지 않는다.

## 조회와 비용 권한

| 작업 | 권한과 기존 제한 |
| --- | --- |
| 공개 공고·저장 개찰 이력·공개 실적 목록/요약 | 기존 익명 공개 GET 유지 |
| 부서 판단/결과 및 비공개 import를 제외한 운영 실적 원장 조회 | 부서 또는 관리자 로그인, 원문 증빙 권한 없음 |
| 판단·결과 작성 | 자기 부서만, 기존 CAS·이력 유지, ADMIN 대리 작성 금지 |
| 최근 3년 업체 낙찰 검색, PPS/사전규격 검색·선택 저장 | 로그인 + 동일 출처/CSRF + 기존 `paid_analysis_allowed=true`; 외부 호출 기간·페이지·시간·건수 상한 유지 |
| 공고/사전규격 명시 추출 | 별도 paid grant, 기존 attachment/call/cooldown/lease/idempotency 유지 |
| 저장 근거만 재판단, 진단, 요청 상태 조회 | 해당 기존 경로의 검증 조건과 로그인 유지; 추출로 넘어가면 paid 권한 재검증 |
| 실적 원장 변경/private import·비공개 증빙·광역 서버 작업 | 부서 cookie에 추가 허용하지 않음; 기존 별도 인증 유지 |

기본 paid=false는 그대로이며 단순 계정 활성화가 외부 API나 모델 사용 권한을 주지 않는다. 유료/외부 조회 권한의 부여는 기존 관리자 API의 별도 명시 작업이며 이번 최소 활성화 UI에 포함하지 않는다. 업체 낙찰 조회 결과는 자동으로 회사 실적이 되지 않는다.

## 중지와 복구

문제가 있으면 새 코드에서 account flag를 끄면 생산 환경의 브라우저 쓰기/유료 요청이 닫힌다. 공개 조회와 기존 서버 간 작업은 유지된다. flag를 다시 켜도 PIN을 복원하지 않는다. 기존 세션을 폐기해야 하는 상황에서는 관리자 세션 취소 API 또는 대상 계정 PATCH를 사용한다. flag만 끄는 것은 DB의 모든 세션을 취소하는 작업이 아니다.

PIN을 받던 과거 앱 버전으로 되돌려 인증 경로를 다시 여는 것을 복구 절차로 사용하지 않는다. 세션 취소나 계정 비활성화는 이미 예약된 서버 작업을 자동 취소하는 기능이 아니다. 진행 중 작업의 중지는 기존 운영 절차로 별도 확인한다. PIN 환경변수는 잔존해도 인증에 사용되지 않으며 운영자가 설정 정리 시 제거할 수 있다.

실제 390px 브라우저·기존 credential 바인딩·운영 계정 활성화 결과는 로컬 합성 검사로 확인할 수 없으므로 운영자 검증이 필요하다.
